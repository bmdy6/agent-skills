# siltop 本机状态检查

用实际采样回答现在是否有压力、谁占用较多、哪些地方还需核查。默认不关闭页面、终止进程、修改配置、安装后台采集器或运行压测；用户明确要求处理时再按具体归属和授权执行。

## 采样

确认 `siltop --version` 可用。首次在这台 Mac 使用或传感器异常时运行 `siltop doctor`；未安装时说明依赖，不自动安装。采样与汇总使用 [scripts/check.py](./scripts/check.py)：

```sh
python3 <技能目录>/scripts/check.py
python3 <技能目录>/scripts/check.py --samples 10
```

脚本默认每秒一次、共 20 次，读取 siltop JSON 和 `ps` 的程序路径，不读取环境变量、命令参数、凭据或浏览器正文，不启动持续服务。它只输出汇总；需要保存证据时重定向到本机临时文件。既有 NDJSON 可用 `--input <文件>` 重新汇总，此模式不读取当前进程路径，避免将历史 PID 归到现在的应用。

## 判断口径

- 优先看内存 pressure、swap_in/out 的区间活动和 thermal_pressure。高 used 或已有 swap 不足以判断正在卡顿；低 free 也不能单独判异常。
- footprint 包括压缩内存；RSS 是驻留页且可能包含共享页。不能将应用合计当作物理内存总量，也不承诺退出会释放同等容量。
- 整机 CPU `usage` 与按频率加权的 `scaled` 不同。进程 CPU 100% 表示一个核心；工具报 Busy 可能只是正常编译或界面忙碌。
- `null` 是未测得；检查 health 与样本覆盖率，不填成零。功耗可能滞后数秒；缺失的 CPU/ANE/DRAM 功耗不能推算出来。
- 按可执行文件所在应用包归类，不把 Codex 的全部子进程算作 Codex 界面。`cli.js`、Node 等名字不能直接判定是飞书或闲置任务。

## 异常进程或关闭候选

发现实例累计后再针对 PID 核对父进程、启动时间、`lsof` 工作目录、监听端口及当前聊天状态。必要时只提取启动命令中的脚本路径，勿输出整行参数或读取进程环境。

页面通过当前浏览器工具读取标题与任务空间归属。其他 Agent 正在使用、用户持有或归属不明的页面只列候选，不接管或关闭。开发服务有连接、刚启动或对应聊天仍运行时，不能仅因暂时 CPU 为零就认定无用。

日志时间吻合只能作为归属线索；没有 PID 绑定时标注推断。配置里 disabled 不证明旧会话已卸载连接。处理后重新采样，并核查实例是否新增；一次清零不能声称永久解决。重启宿主会影响其他任务，须先核清影响与授权。

给出采样时间、当前主要问题、最值得检查的应用及验证边界。短结论直接回复；需要比较候选时再用表格或页面，不强制生成报告。
