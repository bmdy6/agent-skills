# Issue 正反例

以下内容是**虚构示例**，只展示粒度和写法，不代表任何真实项目事实。

## 正例：一个问题、一组验收

**标题：** 已选择网络后，搜索结果仍可能返回其他网络的同名资产

```markdown
## 文档依据

> 用户选定网络后，资产搜索结果应限定在当前网络。

<需求文档链接>

> 搜索按资产符号匹配，可返回同名资产候选。

<另一处文档链接>

两处描述对“是否允许跨网络候选”口径不一致。

## 情报链接

<用户反馈 / 情报链接>

## 现状

用户已经选定 BSC 后搜索同名资产，当前候选列表仍可能包含其他网络的资产。最终定位在搜索候选过滤阶段；相关实现位于 `search_assets.py:120-148`。

## 证据

- 复现：选择 BSC → 搜索测试资产符号 → 返回结果中出现另一网络候选。
- Trace：`trace_demo_001`
- 截图：<紧贴这里放已上传图片>

## 需要确认

用户已经选定网络后，产品希望：

- 只展示当前网络的资产；还是
- 允许其他网络同名资产继续展示，但必须明确标出网络？

## 验收

- [ ] 用户选定某网络后，搜索结果符合最终确认的网络范围规则。
- [ ] 同名资产存在于多个网络时，不会出现无法判断来源的候选。
```

为什么这是一条 Issue：触发条件只有“已选网络后搜索同名资产”，修复动作是“修正候选网络过滤”，验收也是同一组。

## 反例：把两个修复动作揉成一条

**坏标题：** 数据库命中后还继续搜索，并且跨链同名资产会误选

问题 A 是“本地已经命中后是否还应该继续远程搜索”；问题 B 是“远程候选回来后如何按网络筛选”。一个是流程短路，一个是候选过滤。任意一个修完，另一个仍可能存在，因此应拆成两条。

正文也不要这样写：

```markdown
## 排查过程

先 grep 了入口，后来跟到 service，再打日志，发现第一次猜错了……

## 需要确认

`asset_source_kind` 到底该用 `db_hit` 还是 `remote_hit`？
```

前半段是接手者不需要的调查日记；后半段是内部命名，产品无法决定。保留最终定位和证据，把“需要确认”翻译成用户实际看到的行为差异。
