# 写一条可执行的 GitHub Issue

目标：让接手的人不用重走排查过程，就能知道**哪里不对、证据是什么、还差哪个业务决定、怎样算修好**。

本技能只负责 Issue 的粒度、正文和证据呈现。它**不授权发布 Issue**，也不负责决定“要不要提”、跟踪、关闭或拆整套项目计划；计划拆票用 `to-tickets`。

## 1. 先判断：这是一条还是两条 Issue

一条 Issue 只解决一个可独立修复、可独立验收的问题。判断时看三个问题：

1. **修复动作是不是同一个？** 如果 A 修数据库短路、B 修跨链筛选，属于两条。
2. **能不能独立修好并关闭？** 任一问题修完后另一个仍成立，就应拆开。
3. **验收是否同一组？** 两套不同触发条件或验收结果，通常应拆。

标题出现“并 / 同时 / 以及”或包含两个独立动作时，只当作**拆分警报**，不是机械规则；最终以修复动作和独立验收为准。

如果应拆，先明确告诉用户“这是两个独立问题”，分别起标题和正文；不要为了省事揉成一条大 Issue。

## 2. 正文只放接手者需要的事实

按证据强度整理，不写排查日记：

- **事实边界**：只写用户提供或已经核实的事实。缺链接、trace、坐标或复现条件时写 `<待补>` 或省略，不根据常识补“可能导致 loading / 资损 / 超时 / 返回某个 id”等未验证影响、根因或结果。

- **文档依据**：贴最相关原文和链接。文档前后矛盾时，两句都贴出来并标明冲突，不替产品选答案。
- **情报链接**：放触发本问题的外部情报、用户反馈或原 Issue 链接；没有就省略，不造链接。
- **现状**：一句用户可理解的现象 + 必要的代码坐标（文件/行号/函数）。只写最终定位，不写 grep 过程、调用链摸索、中间脚本和走过的弯路。
- **证据**：最小复现、trace ID、关键日志、截图。日志只截能证明问题的几行。
- **需要确认**：只问产品/业务能回答的口径，不出现文件路径、函数名、枚举名、字段名或内部标签。能从文档/代码直接确认的不要再问产品。
- **验收**：只写用户明确目标、文档已确认行为或已经验证的边界，并写成用户可观察结果；用户没说明的“其他场景保持不变 / 某失败路径也应怎样”不要自行补，必要时标 `<待确认>`。不把“改某函数 / 加某字段”当验收。

## 3. 默认正文结构

默认按下面顺序。`现状 / 证据 / 验收` 必须有；没有文档、情报或待确认项时，对应章节直接省略，不写“无 / 暂无”空壳。

```markdown
## 文档依据

> <最相关原文>

<文档链接>

## 情报链接

<反馈 / 情报 / 上游 issue 链接>

## 现状

<当前用户可见问题。必要时补 文件:行号 / 函数。>

## 证据

- 复现：<最小步骤>
- Trace：<trace id / request id>
- 截图：<图片紧贴对应证据>

## 需要确认

<只写业务口径问题；如果没有真正需要产品拍板的内容，整节省略。>

## 验收

- [ ] <用户可观察结果 1>
- [ ] <边界 / 失败场景结果 2>
```

## 4. “需要确认”先翻译成业务语言

坏问题通常长这样：

> `result_kind=content` 是否应该改成 `source_content`？

产品无法判断内部命名。先翻译成用户看到的差异：

> 同一个资产同时存在于两条链时，用户已经选定 BSC 后，搜索结果应只保留 BSC，还是允许同时展示其他链并标明来源？

如果两个文档写法冲突，把冲突原文放在“文档依据”，然后在“需要确认”只问**最终业务行为选哪个**。

## 5. 截图是证据，不是装饰

- 大图先压到**约 1400 px 宽以内**，保持宽高比；不要把 3000 px 截图原样塞正文。
- 图片紧贴它证明的那条现象，正文不再逐字复述图里已经看清的内容。
- 本地图片要先上传成 GitHub `user-attachments` URL；`gh issue create --body-file` **不会替你上传本地图片**。
- 优先使用当前 `ego-browser` 的公开文件上传 API，不写死 GitHub DOM 或 raw CDP 私有流程。
- `<img>` 同时写 width/height 时必须使用**压缩后的真实尺寸**；更稳妥的是只写 width 让浏览器保持比例。

需要处理本地截图时再读 [`references/image-evidence.md`](references/image-evidence.md)。

## 6. 发布前 20 秒检查

- [ ] 标题只描述一个问题；修复动作和验收只有一组。
- [ ] 没把另一个可独立关闭的问题顺手塞进来。
- [ ] 正文没有排查流水账、无关调用链或中间产物。
- [ ] 文档冲突原样保留，没有替产品擅自拍板。
- [ ] “需要确认”是业务语言，没有代码内部命名。
- [ ] 截图尺寸合适、紧贴证据、能正常渲染；图里已有的信息没有再写一遍。
- [ ] 验收描述用户结果，不是实现步骤。

完整正反例见 [`references/examples.md`](references/examples.md)。
